# Enterprise RAG Knowledge Base

基于 **BM25 + 向量混合检索、规则重排序** 的 RAG（Retrieval-Augmented Generation，检索增强生成）企业知识库问答后端。
使用 FastAPI 对外提供 HTTP 接口，LangChain（LCEL）编排检索与生成链路，DeepSeek 作为生成模型，Redis 作为**可选**查询缓存。

核心链路：用户提问 → 双路混合召回候选片段 → 规则重排精筛 → 仅依据检索到的上下文让大模型作答（约束其不得编造）→ 返回答案与引用来源。

---

## 功能特性

- **混合检索**：BM25 关键词路（中文按单字切分）+ FAISS 向量语义路双路召回；两路分数各自归一化到 [0, 1] 后按 `0.6 * 向量 + 0.4 * BM25` 加权融合，兼顾字面精确匹配与语义泛化。
- **两级检索漏斗**：检索阶段粗召回 Top-10，重排阶段精留 Top-4 再送入 LLM，在"召回完整"和"上下文不被噪声稀释、节省 token"之间取平衡。
- **零模型依赖的重排器**：规则 Reranker 综合精确命中、关键词重叠、原始名次、文档长度四类特征重新打分，不需要额外下载模型；类接口与 Cross-Encoder 重排器保持一致，可直接替换。
- **缓存可降级**：Redis 连接失败、读写异常时自动降级为无缓存模式，**缓存层任何故障都不会中断主问答链路**。
- **答案可溯源**：响应中携带每一条引用片段及其融合得分，便于核对答案出处。
- **防幻觉约束**：系统提示词强制模型"只根据给定上下文回答，上下文没有就明确说未找到，禁止编造"。
- **开箱即用**：服务启动时自动完成文档切分、Embedding 与索引构建；内置 26 段模拟企业文档（公司介绍、产品矩阵、休假、报销、差旅、IT 支持、绩效、采购、安全合规、研发流程等），并自动打开 Swagger 交互文档。
- **可复现的离线消融评测**：`evaluate.py` 提供 BM25 / 纯向量 / 混合检索 / 混合+重排四路对比，基于 65 题人工标注评测集输出 Recall@K 与 MRR，实验结果与分析见下文"检索消融实验"章节。

## 技术栈

| 层级 | 选型 | 说明 |
|------|------|------|
| Web 框架 | FastAPI + Uvicorn | 路由、参数校验、自动生成 OpenAPI/Swagger 文档 |
| 链路编排 | LangChain / LCEL | 以管道方式组装 Prompt、LLM、输出解析器 |
| 生成模型 | DeepSeek `deepseek-chat` | 兼容 OpenAI 协议，经 `ChatOpenAI` 接入 |
| Embedding | `BAAI/bge-small-zh-v1.5` | 本地中文句向量模型，输出 L2 归一化向量 |
| 向量索引 | FAISS（faiss-cpu，内存） | `IndexFlatL2` 精确最近邻检索 |
| 关键词检索 | rank-bm25（BM25Okapi） | 经典词法检索，与向量路互补 |
| 缓存 | Redis（可选，可降级） | 查询结果缓存，默认 TTL 3600s |
| 配置管理 | pydantic-settings | 环境变量 / `.env` 覆盖默认配置 |
| 数据校验 | Pydantic v2 | 请求与响应模型校验、序列化 |

## 快速开始

### 1. 环境与依赖

要求 Python 3.10+。

```bash
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

> 首次运行会从 HuggingFace 下载 `bge-small-zh-v1.5` 模型。代码中已将 `HF_ENDPOINT` 指向国内镜像 `hf-mirror.com`；如已配置本地模型缓存则无需联网。

### 2. 配置（可选但建议）

在项目根目录创建 `.env` 文件（不配置则使用 `config.py` 中的默认值，但没有 API Key 无法调用生成模型）：

```env
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
DEEPSEEK_BASE_URL=https://api.deepseek.com/v1
DEEPSEEK_MODEL=deepseek-chat

REDIS_URL=redis://localhost:6379/0
REDIS_TTL=3600
```

Redis 为可选项：**本机没有启动 Redis 也能正常运行问答**，日志会提示缓存已自动关闭。

### 3. 启动

```bash
# 方式一：直接运行（已处理项目根目录的导入路径，并自动打开浏览器文档页）
python app/main.py

# 方式二：标准 Uvicorn 启动
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## API

### `GET /` 健康检查

返回服务状态与缓存是否可用。

### `POST /query` 知识库问答

请求体：

```json
{
  "question": "公司的年假是怎么规定的？",
  "top_k": 4
}
```

- `question`：必填，非空字符串；
- `top_k`：可选，范围 1~20，默认 4，即重排后最终使用的上下文条数。

响应体：

```json
{
  "question": "公司的年假是怎么规定的？",
  "answer": "根据公司制度，入职满一年享有 5 天年假……",
  "sources": [
    {
      "content": "公司休假制度如下：入职满一年享有5天年假……",
      "score": 0.8321,
      "source": "knowledge_base"
    }
  ],
  "cached": false
}
```

- `sources`：实际引用的文档片段及得分，用于答案溯源；
- `cached`：本次结果是否来自缓存。

## 核心实现（按数据流）

### 1. 文档加载与切分（`rag/store.py`）

1. 以空行切分原始文本得到自然段落，每段包装为 LangChain `Document`（正文 + `metadata.source`）；
2. 使用 `RecursiveCharacterTextSplitter` 做递归切分：按 `["\n\n", "\n", "。", "；", "，", " ", ""]` 的分隔符**逐级降级**，尽量在语义自然的边界断开，适配中文；
3. `chunk_overlap` 让相邻块保留重叠，避免关键信息被切断在两个块中。

### 2. Embedding 与向量索引

- 使用 `bge-small-zh-v1.5` 对每个 chunk 编码，并开启 `normalize_embeddings=True` 做 L2 归一化；
- `FAISS.from_documents` 在内存中构建 `IndexFlatL2` 精确索引；
- 向量库与文档列表在模块导入时一次性构建并以模块级单例常驻内存。

### 3. 混合检索（`rag/retriever.py`）

- **BM25 路**：rank-bm25 不自带中文分词，因此用正则把中文按单字、英文/数字按整词切分，构造 `BM25Okapi`；对全库打分后除以最大值做 min-max 归一化；
- **向量路**：FAISS 返回 L2 距离（越小越相似），用 `1/(1+dist)` 单调映射到 (0, 1] 的相似度；
- **融合**：以 chunk 内容为键对两路结果取并集，缺失路记 0 分，按 `0.6*vec + 0.4*bm25` 融合后降序取 Top-10。

### 4. 规则重排（`rag/reranker.py`）

对每个候选计算四类规则特征并加权：精确子串命中（0.35）、关键词重叠（0.30）、原始名次因子（0.20）、长度因子（0.15）；再与混合检索原始分按 0.5/0.5 融合，最终取 Top-K。

### 5. LCEL 生成链路（`rag/chain.py`）

用 LCEL 管道 `组装字典 | Prompt 模板 | ChatOpenAI | StrOutputParser` 串联：

- `RunnablePassthrough` 透传用户问题，闭包注入已重排好的上下文；
- Prompt 明确要求"严格依据上下文、无依据则声明未找到、禁止编造"；
- `temperature=0.3`，在可回答性与稳定性之间偏低随机性；
- 输出答案的同时返回引用片段与得分。

### 6. 缓存与降级（`services/cache.py`）

- 启动时 `ping` 探测 Redis，失败则将客户端置空、关闭缓存而非抛错；
- key 为 `rag:query:` 前缀 + `MD5(question)`，value 为 JSON，默认 TTL 1 小时；
- 每次 `get/set` 均捕获异常并降级，保证缓存问题永远不向上扩散到问答主链路。

## 检索消融实验

为量化各检索组件的真实贡献，基于 26 段企业知识库、65 道人工标注问答对（覆盖语义改写题与专名/数字题），运行四路离线消融实验。评测脚本为 `evaluate.py`，不依赖 LLM API，仅评估检索与重排环节。

### 实验设置

- **知识库**：26 段企业制度与产品文档，经 `RecursiveCharacterTextSplitter` 切分后共 26 个 chunk
- **评测集**：65 道问答对，每题标注标准答案段落（gold），其中语义改写题约占 40%，专名/数字精确匹配题约占 60%
- **四路对比**：
  1. **BM25**：纯关键词检索（中文单字切分）
  2. **Vector**：纯向量语义检索（FAISS + bge-small-zh-v1.5）
  3. **Hybrid**：BM25 + 向量加权融合（0.6×vec + 0.4×bm25），不重排
  4. **Hybrid+Rerank**：混合检索后经规则重排（精确匹配/关键词重叠/名次/长度四特征）
- **指标**：Recall@1 / Recall@4 / Recall@10 / MRR@4

### 实验结果

| 方法 | Recall@1 | Recall@4 | Recall@10 | MRR@4 |
|------|----------|----------|-----------|-------|
| BM25 | 93.8% | 98.5% | 100.0% | 0.962 |
| Vector | 84.6% | 93.8% | 100.0% | 0.887 |
| **Hybrid** | **95.4%** | **100.0%** | 100.0% | **0.977** |
| Hybrid+Rerank | 93.8% | 100.0% | 100.0% | 0.969 |

### 结果分析

1. **混合检索全面优于单路检索**：Hybrid 在 Recall@1 上比 BM25 高 1.6 个百分点、比 Vector 高 10.8 个百分点；Recall@4 达到 100%，而 BM25 为 98.5%、Vector 仅 93.8%。验证了"词法精确匹配 + 语义泛化"双路融合的互补价值。

2. **纯向量检索在精确事实题上存在语义漂移**：Vector 有 4 题在 Top-4 未命中（如"公司在海外哪个城市有研发中心""生产环境操作日志保留多久"），均为答案含专名或数字的事实题。向量模型倾向于将语义相近但事实不同的段落排在前面，这是纯语义检索的典型短板。

3. **BM25 在本评测集上表现强劲**：Recall@1 达 93.8%，仅 1 题未命中（"公司规定的工作时间是怎样的"——该题为语义改写，BM25 无法匹配"工作时间"与"9:00-18:00"的语义关联）。这说明在专名/数字密集的企业制度场景中，关键词检索仍是不可替代的基线。

4. **规则重排未带来增益，反而略降**：Hybrid+Rerank 的 Recall@1（93.8%）和 MRR@4（0.969）均低于纯 Hybrid（95.4% / 0.977）。根因分析：
   - `exact_match` 特征（权重 0.35）判断"完整查询是否为文档子串"，对自然语言问题几乎从不触发，35% 的规则分恒为零；
   - `position` 特征（权重 0.20）仅按原始名次给分，与检索原始分高度冗余，不提供新信息；
   - `length` 特征（权重 0.15）无条件偏好长文档，偶尔将信息密度低但篇幅长的干扰段落推高；
   - 仅 `keyword_overlap`（权重 0.30）提供有效信号，但不足以抵消其余三项的噪声。
   - **结论**：基于启发式规则的重排器在特征设计上存在缺陷，应替换为 Cross-Encoder 类重排模型（如 bge-reranker），通过"查询-文档"联合编码实现真正的精排。

## 关键设计取舍

- **为什么要双路检索而不是只用向量？** 向量检索擅长语义近似但对专有名词、数字、型号不敏感；BM25 擅长精确词匹配但不懂同义/近义。两者归一化后融合，召回更稳。
- **为什么两路分数要先归一化再相加？** BM25 原始分量纲不固定、向量相似度在 [0,1]，直接相加会被数值大的一路主导，融合失效。
- **为什么召回 10 条却只给模型 4 条？** 检索阶段优先保证召回率，重排阶段优先保证精度；送入 LLM 的上下文过多会稀释关键信息、抬高 token 成本与延迟。
- **Redis 为什么设计成"可降级"而不是强依赖？** 缓存的定位是加速手段，不应成为问答可用性的单点；缓存故障时系统退化为"慢一点但能用"。
- **为什么路由函数用同步 `def` 而非 `async def`？** 检索与 SDK 调用均为同步阻塞逻辑，FastAPI 会把同步路由放到线程池执行，避免阻塞事件循环。
- **为什么 Embedding 要做归一化？** 归一化后向量为单位向量，内积等价于余弦相似度，距离尺度稳定，便于和 BM25 分做同尺度融合。
